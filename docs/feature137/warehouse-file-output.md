## 2. ファイルの形式

### 2.1 ヘッダファイル（1 注文 1 行）

`バッチID,業務日,注文番号,受取人,郵便番号,都道府県,市区町村,住所,電話番号,税抜き金額,税額,合計金額`

- 合計金額 = `orders.total_amount`（税込）、税額 = `orders.tax_amount`、税抜き金額 = 合計金額 − 税額。
- バッチID：①はバッチの id（数字。③の照合に必要なので今のまま）、②は `E` + 緊急出荷記録の id。
- 業務日：①はバッチの業務日、②は緊急出荷の操作日（`prepared_at` の日付）。今と同じ。
- 行の並び：注文番号の昇順。

### 2.2 明細ファイル（1 明細 1 行。送料が 1 円以上なら送料の行を最後に追加）

`バッチID,注文番号,明細番号,商品ID,商品名,税率,単価,数量,小計,税額`

- 商品の行：`order_items` を id の昇順で並べ、明細番号を 1 から振る。
- 送料の行：`order_charges`（SHIPPING、金額が 1 円以上）を商品の行に続けて並べる。商品ID は空欄、商品名は記録されている名前（「送料・梱包料」）、単価は送料の金額、数量は 1、小計も送料の金額。
- 税率：`10%` / `8%`（半角。保存されている税率 10.00 → `10%`）。
- 行の並び：注文番号、明細番号の昇順。

### 2.3 明細ごとの税額（決定 A）

注文の税額は「税率ごとに 税込合計 × 税率 ÷ (100 + 税率) を計算し、1 円未満を切り捨てて合計」です（`TaxCalculator`）。明細ごとに切り捨てた税額を足すと、この値より少なくなることがあります（開発 DB では 25 注文中 2 注文で 1 円の差）。

決定（A）：
1. 税率ごとの税額を `TaxCalculator` と同じ計算で出す。
2. その税率の各明細の税額を、小計 × 税率 ÷ (100 + 税率) の切り捨てで出す。
3. 税率ごとの税額と各明細の税額の合計との差（明細の数より小さい）を、その税率で小計が最も大きい明細（同じ額なら明細番号が小さい方）に足す。

これで「明細の税額の合計 = ヘッダの税額 = `orders.tax_amount`」になります（開発 DB の全 25 注文で、税率ごとに計算し直した合計が `tax_amount` と一致することを確認済み）。

### 2.4 照合（アプリと DB の両方）

- 注文ごとに、明細の小計の合計 = ヘッダの合計金額、明細の税額の合計 = ヘッダの税額。
- ヘッダの行数 = 注文の数、明細の行数 = 商品の行数 + 送料の行数。

### 2.5 ファイル名

- `warehouse-header-<業務日 yyyyMMdd>-<バッチID>.csv` / `warehouse-detail-<業務日 yyyyMMdd>-<バッチID>.csv`
- 例：①は `warehouse-header-20261121-15.csv`、②は `warehouse-header-20261121-E3.csv`。
- 同じ出力対象に対しては、何度出力しても同じ名前・同じ内容になる（元のデータが変わらないため）。

### 2.6 出力するものがない日（決定 C）

封印した①のバッチの出力行が 0 件のときも、ヘッダー行だけのファイルを 2 つ出力する（倉庫が「今日は 0 件」と分かるようにするため）。

## 3. 元にするデータ

- ①：`warehouse_export_lines` に保存した内容から作る。V101（137-A で実装）で次の 2 列を追加し、出力行を書き込むときに新しいトリガー `f137_line_file_snapshot`（`f131_line_guard`・`f135_line_expiry_guard` のあとに動く）がロックした注文から写し取る。呼び出し側が値を指定しても上書きする。既存の `items` 列は変えない。
  - `tax_amount`（注文の税額）
  - `file_lines`（JSONB。明細ファイルの行そのもの：lineNo, orderItemId, orderChargeId, productId, productName, taxRate, unitPrice, quantity, subtotal, taxAmount）。付帯料金は金額が 1 円以上のものをすべて含める（今は送料だけ）。
  - 小計の合計が注文の合計金額と、税額の合計が注文の税額と一致しなければ書き込みを拒否する（23514）。アプリは注文の出荷準備を始める前に同じ照合を行い、一致しなければ保留にする（保留理由を追加：`AMOUNT_MISMATCH`「明細・税額が注文金額と一致しない」）。
- ②：出荷準備を始めた注文は、明細・送料・金額がトリガーで凍結されている（V98）ので、注文から作る。
- 2.3 の計算は SQL 関数（`f137_order_file_lines(order_id)`）を 1 つだけ用意し、①のトリガーと②の生成の両方で使う。
- V101 より前に保存した出力行（開発 DB のバッチ 1 件）には税額がないので、ファイルは出力しない（旧形式のまま、出力の対象外）。
- アプリ側（137-A）：`WarehouseFileFormat`（2 ファイルの生成と照合。DB を使わない）、`WarehouseFileSource`（①は封印したバッチの `file_lines`、②は緊急出荷記録の注文と `f137_order_file_lines` から内容を読む）。ファイルの書き出しは 137-B で行う。
- テストの注文データ：これまでテスト用の注文は `tax_amount` などが 0 のままだった（実際の注文確定では必ず設定される）。倉庫出力を使う 3 つのテストクラスで、注文確定と同じく金額を設定するようにした。

## 4. 出力の流れ

### 4.1 出力記録（V102 `warehouse_file_outputs`）

1 出力対象（①のバッチ 1 件、または②の緊急出荷記録 1 件）につき 1 行。

| 列 | 内容 |
|---|---|
| kind | `REGULAR` / `EMERGENCY` |
| batch_id / emergency_shipping_preparation_id | どちらか一方だけ（CHECK）。それぞれ一意 |
| business_date, header_filename, detail_filename | トリガーが決める |
| state | `PENDING` → `WRITTEN` / `FAILED`、`FAILED` → `PENDING`（再出力） |
| attempts, next_attempt_at, claimed_until, last_error | 再試行の管理 |
| header_row_count, detail_row_count, header_sha256, detail_sha256, written_at | `WRITTEN` のときだけ必須 |

- 行を作るのはトリガー：①はバッチを封印したとき（OPEN → SEALED）、②は `emergency_shipping_preparations` に行を追加したとき。どちらも、その処理と同じトランザクションの中で作るので、出力の漏れが起きない。V102 より前のバッチと緊急出荷記録には作らない。V101 より前の出力行（旧形式）を含むバッチにも作らない。
- 実装（137-B、V102）：作成時にトリガーがバッチまたは緊急出荷記録から、出力バッチID（数字／`E`＋記録ID）・業務日・ファイル名・ヘッダの行数・明細の行数を決める（呼び出し側の値は使わない）。ファイル名・行数などの定義は変更できない（55000）。アプリは書き出す前に、作った内容のファイル名と行数がこの記録と一致することを確認する。
- `WRITTEN` にするには試行回数の加算と 2 ファイルの SHA-256 が必要（23514）。出力時刻（`written_at`）と試行時刻は DB の時計で決める。`WRITTEN` からはどこへも移れない。
- `FAILED` → `PENDING` は、同じトランザクションで `warehouse_file_output_retries` に管理者の行を追加したときだけ（その行の追加トリガーが戻す）。直接の更新は拒否する（55000）。
- 削除・TRUNCATE はできない（55000。出力記録だけの TRUNCATE は、再出力の外部キーにより PostgreSQL が先に拒否する）。決めた状態遷移以外は拒否する。

### 4.2 書き出し（DB トランザクションの外）

1. 出力待ちの行を `FOR UPDATE SKIP LOCKED` で 1 件選び、`claimed_until`（例：5 分後）を設定してコミットする。
2. トランザクションの外でファイルを作り、作業フォルダーに一時ファイルとして書く（fsync）。
3. 2.4 の照合をアプリで行う。
4. 明細ファイル → ヘッダファイルの順に、出力フォルダーへ `ATOMIC_MOVE` で移す。FTP 側には「ヘッダがあれば明細もそろっている」と伝える。
5. 別のトランザクションで `WRITTEN` にし、行数と sha256 を記録する。
- 出力フォルダーに同じ名前のファイルがあるとき：内容が同じなら完了として扱い、違えば上書きせずに失敗とする。
- 失敗したら `attempts + 1`、`next_attempt_at` を 5 分後にする。上限（例：12 回 ≒ 1 時間）に達したら `FAILED`。
- **二重出力の可能性（決定 D：この前提で問題なし）**：ファイルを移したあと、`WRITTEN` を記録する前にアプリが止まると、再試行で同じファイルをもう一度出力することがある。FTP 側がすでに持ち去っていると、それが二重出力になる。ファイル名と内容は毎回同じなので、倉庫側で重複を見分けられる。

### 4.3 再出力（管理画面）

- `FAILED` の行だけ「再出力」できる（`WRITTEN` の行は出し直さない＝再取得はしない）。
- 押すと `PENDING`・`attempts = 0` に戻し、管理者・時刻を追記のみの監査テーブル（`warehouse_file_output_retries`）に記録する。すべての管理者が操作できる。

### 4.4 設定（`.env` は書き換えず、環境変数で指定）

| プロパティ | 環境変数 | 既定値 |
|---|---|---|
| `app.warehouse-file.enabled` | `WAREHOUSE_FILE_ENABLED` | false |
| `app.warehouse-file.output-dir` | `WAREHOUSE_FILE_OUTPUT_DIR` | なし（有効にするなら必須） |
| `app.warehouse-file.work-dir` | `WAREHOUSE_FILE_WORK_DIR` | なし（出力フォルダーと同じファイルシステムで、FTP の対象外の場所） |
| `app.warehouse-file.fixed-delay` | `WAREHOUSE_FILE_FIXED_DELAY` | 1m |
| `app.warehouse-file.retry-delay` / `max-attempts` / `claim-lease` / `batch-size` | — | 5m / 12 / 5m / 20 |

無効のあいだも出力記録は `PENDING` で作られ、ダッシュボードで見える。有効にしたら古い順に出力する。有効にして出力フォルダーか作業フォルダーが未指定なら、アプリは起動しない（設定の誤り）。フォルダーがない・別のファイルシステムにあるなどの場合は、試行の失敗として記録し、理由を画面に表示する。

実装（137-B）：`WarehouseFileOutputStore`（記録の取得・完了・失敗・再出力）、`WarehouseFileWriter`（ファイルの書き出し）、`WarehouseFileOutputService`（1 回の処理）、`WarehouseFileOutputScheduler`（有効なときだけ動く）、`AdminWarehouseFileOutputController`（`POST /admin/warehouse-file-outputs/{id}/retry`）。失敗理由は、アプリが作った説明文だけを記録・表示する（それ以外の例外は種類名だけ。SQL の本文には注文の情報が含まれうるため）。
