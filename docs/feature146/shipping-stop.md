# Feature146 出荷中止

状態：設計は承認済み（2026-11-27、1〜6 とも案のとおり）。146-A は実装・テスト済み（第 11 章）。146-B は未着手。基準は main 2dc2241（最新マイグレーション V113）。

## 1. 目的

出荷準備を始めたが、まだ出荷していない注文を、管理者が理由を記録して取り消せるようにする。出荷準備は、14:05 の倉庫向け出力でも、緊急出荷でも始まる。

想定する場面は次のとおり。

- 倉庫で在庫切れや破損が見つかった。
- 出荷前にお客様から強い取消の申し出があった。
- 倉庫での滞留中に与信の期限が切れ、出荷しても売上を確定できない。

## 2. 調査結果（2026-11-27、main 2dc2241）

### 2.1 今の決まり

- 出荷準備を始めた注文は、内容と状態が固まる（V98 `f131_prepared_content_guard`）。CANCELLED への変更も DB が拒否する。アプリも `Order.requireContentMutable()` で拒否する。
- 変更の期限（14:00）より後の注文の取消（目的 ORDER_CANCELLATION の CANCEL 取引）は、与信の期限切れによる取消（Feature135、V94）だけが認められる（`f135_late_cancellation_guard`）。
- 与信の期限切れによる取消（Feature135）は、出荷準備を始めた注文を対象外にしている（`requireCancellableUnprepared`）。
- 倉庫向けファイルの中身は、変わらない記録から作られる。
  - 14:05 の分：`warehouse_export_lines` から作る。
  - 緊急出荷の分：出荷準備の記録と注文から作る。
  - このため、書き出す前に取り消しても、ファイルには取り消した注文が入る。倉庫が受け取ったファイルを、システムから取り消す方法はない。
- 出荷済み CSV の取り込みは、ORDERED と PAID 以外の注文を出荷しない（`WarehouseShipmentImportWorker`）。
- 緊急出荷は、権限 `admin_accounts.emergency_shipping_allowed` を持つ管理者だけが行える（Feature136）。

### 2.2 今起きること

- 出荷準備を始めた注文は、出荷するしかない。与信の期限が切れると、出荷しても売上の確定が失敗する（Feature135-B2）。
- 開発 DB には今、出荷準備済みで未出荷の注文はない。8 件はすべて出荷済み。

## 3. 範囲

- 対象：出荷準備を始めていて（`shipping_preparation_started_at` あり）、状態が ORDERED か PAID で、出荷していない注文。
- 次の場合は対象外（拒否する）：
  - 売上確定の処理中（`capture_requests` の未完了、取り込みの行が PENDING か CAPTURE_UNCONFIRMED）
  - 未完了の注文変更か、決済の処理中
  - 有効な決済が PAY.JP の 1 件でない
- 対象外：出荷済みの注文の返金と返品（別の Feature）。出荷中止のあとで出荷準備をやり直すこと（取り消すだけにする）。

## 4. 流れ

1. 管理者が注文詳細で「出荷を中止して取り消す」を押す。
   - 入力：理由（必須、500 文字以内）
   - 確認：「倉庫に出荷しないよう連絡した」のチェック（必須）
   - 画面には、倉庫向けファイルの状態（書き出し済みか、待ちか）を表示する。
2. 与信の状態で分ける。
   - **与信が期限切れ**（記録上の期限が過ぎている）：Feature135 と同じく、PAY.JP を GET する。`canceled` と確かめられたら、1 つの TX で次を行う。POST は送らない。
     - 出荷中止の記録
     - 取消取引（SUCCEEDED）の記録
     - 注文を CANCELLED にする
     - 在庫を戻す
   - **与信が有効**：既存の管理者による取消（`AdminPaymentCancellationService`）と同じ流れで、PAY.JP に取消を送る（POST）。流れは次のとおり。
     - 1 つ目の TX で、出荷中止の記録（REQUESTED）と取消取引（PENDING）を作る。
     - TX の外で POST を送る。
     - 結果の TX で、注文を CANCELLED にし、記録を COMPLETED にする。
     - 結果が不明なときは、既存の照合で確かめる。PAY.JP が拒否したときは、記録を REJECTED にする。注文は出荷準備済みのまま。
3. お客様には、既存の取消メール（ORDER_CANCELLED、V91）が送られる。期限切れのときは、Feature135-C2 の文面になる。

## 5. DB（V114）

- 新しい表 `order_shipping_stops`
  - 注文、理由、管理者、倉庫への連絡の確認
  - 与信の種類（EXPIRED か VALID）
  - 取消取引
  - 状態：REQUESTED、COMPLETED、REJECTED
  - 倉庫向けファイルの状態の写し
  - 作成日時（DB の時計）
  - 追記と、決まった状態の遷移だけ。注文ごとに、未完了の記録は 1 件まで。
- 変える既存の守り
  - `f131_prepared_content_guard`（V98）：出荷準備済みの注文の CANCELLED への変更を、その TX で COMPLETED になる出荷中止の記録があるときだけ認める。それ以外の項目は、今までどおり固める。
  - `f135_late_cancellation_guard`（V94）：変更の期限後の ORDER_CANCELLATION を、出荷中止の記録に結び付いたものも認める。
- 新しい守り
  - 出荷中止の記録を作れるのは、`emergency_shipping_allowed` の管理者だけ（DB でも確かめる）。
  - 記録の条件（出荷準備済み、未出荷、売上確定の処理中でない）を DB でも確かめる。
- 変える関数は、最新の定義の全文を写し、出荷中止の分岐だけを加える。

## 12. 146-B の設計案（2026-11-27、12.4 は 1〜5 とも案どおり承認）

与信が有効な、出荷準備済みで未出荷の注文の出荷中止。PAY.JP に取消を送る（POST）。

### 12.1 調査結果（main 16003de）

- 管理者の取消（`AdminPaymentCancellationService`）の流れ
  1. 開始の TX：取消の取引（PENDING）を作る。
  2. TX の外：POST を送る。
  3. 結果の TX：決済と注文を取り消す。
- POST の結果の種類
  - 結果は CANCELLED か PENDING の 2 つだけ。
  - 通信の失敗や PAY.JP のエラーは `PaymentGatewayException` になる。取引は PENDING のまま残る。
- PENDING の取消の決着
  - 経路は 3 つ：管理者の再操作（GET）、Webhook、照合。
  - 3 つとも、管理者の取消は `AdminPaymentCancellationResultService.apply` に集まる。
  - CANCELLED のときは、そこで `cancelOrderAfterPaymentCancellation` が注文を取り消す。
- 失敗で終わる経路がない：取消の取引を FAILED にする経路は、今はない。PAY.JP が取消を拒否したとき、取引は PENDING のまま残る。
- 期限後の通常の取消
  - Java：`orderModificationGuard` が拒否する。
  - DB：V94 がコミット時に拒否する。
  - 出荷準備済みの注文は、ふつう変更の期限（14:05）を過ぎている。
- 出荷準備済みの注文の取消は、V98（V114 で変えたもの）が、同じ TX で出荷中止を記録したときだけ認める。結果の TX は開始の TX と別なので、このままでは取り消せない。

### 12.2 流れ

1. 管理者が注文詳細で、理由と倉庫連絡の確認を入れて、「出荷を中止して取り消す」を押す（146-A と同じ欄）。
2. 開始の TX：注文をロックし、次の 2 つを作る。
   - 出荷中止の記録（与信の種類 VALID、状態 REQUESTED）
   - 取消の取引（ORDER_CANCELLATION、PENDING）
3. TX の外：PAY.JP に取消の POST を送る（既存の冪等キー、既存の送信前ガード）。
4. 結果
   - **canceled**：結果の TX で次を行う。
     - 決済を取り消す。
     - 記録を COMPLETED にする。
     - 注文を取り消し、在庫を戻す。
     - お客様には通常の取消メールが送られる（期限切れの文面ではない）。
   - **結果がわからない**（通信の失敗、5xx、PENDING）
     - 記録は REQUESTED のまま。注文は出荷準備済みのまま。
     - 決着は、ほかの管理者の取消と同じく、管理者の「PAY.JP で再確認」（GET）、Webhook、照合で行う。
     - 3 つの経路の結果は、`AdminPaymentCancellationResultService.apply` に集まる。出荷中止の記録がある取引なら、そこで出荷中止として完了させる。
   - **PAY.JP が拒否した**（決まった 4xx）：記録は REQUESTED のまま。画面に拒否された旨を出し、「中止を取りやめる」（12.4 の 2）を案内する。

## 14. 146-C：中止した注文の有効な決済（2026-11-27）

### 14.1 見つかったこと

- 146-B のブラウザでの確認（注文 37）で、PAY.JP での取消は通ったのに、結果の反映が止まった。
  - 止めたのは、アプリの確認（`Order.requireContentMutable`）。メッセージは「発送準備を開始した注文は変更・キャンセルできません。」。
  - 記録は REQUESTED、取消取引は PENDING、注文は発送準備済みのまま残った。決まりの上では矛盾のない状態。
- 原因：取消の反映（`PaymentService.applyCancellationResult`）は、注文の有効な決済（`active_payment_id`）を空にする。発送準備済みの注文では、この列はアプリでも DB（V98）でも変えられない。
- テストで見つからなかった理由：テストの注文は、有効な決済が空の古い形だった。
  - 開発環境の注文は、37 件中 26 件で、この列が埋まっている。
  - 146-A（期限切れの与信）の中止も、同じ処理を通る。

### 14.2 直し方（案 A、承認済み）

- 発送準備済みの注文の取消を反映するときは、有効な決済を空にしない。中止した注文は、取り消した決済を指したまま残る。
  - DB は、取消済みの注文が、その決済を指したまま残ることを認めている（V69）。マイグレーションは加えていない。
  - 発送準備済みの注文を取り消せるのは、出荷中止を完了させる TX だけ（V98・V115）。そのため、この分岐を通るのは出荷中止だけ。
- 通常の取消（有効な決済を空にする）とは形が違う。どの決済を取り消したかは残る。
