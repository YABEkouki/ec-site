# Feature142 決済が完了していない注文を終わらせる

状態：設計は 2026-11-25 に承認。142-A は統合・ブラウザ確認済み（main b9d0379）、142-B は統合・ブラウザ確認済み（main 57fdbc7）。結果は 12・13 章。基準は main 2aa58dd（最新マイグレーション V109）。

## 1. 目的

- 決済画面の途中で止まった注文（正式受注前）を終わらせ、確保した在庫を戻す。
- PAY.JP の決済が取り消されたと確認できるまで、注文の取消と在庫の戻しは行わない。
- 取消の送信と与信の成立が重なっても、「正式受注済みなのに与信が取り消されている」状態を作らない。

## 2. 調査結果

### 2.1 現状（開発 DB：注文 26・33）

- 注文の作成時に在庫を確保し、PAY.JP の Payment Flow を作る。その後お客様が離れると、注文 ORDERED・決済 PENDING・AUTHORIZE PENDING のまま残る。
- お客様と管理者のキャンセル、与信期限切れの取消は、どれも使えない。定期照会は canceled を観測したときだけ終わらせ、経過時間では終わらせない。
- canceled を観測すると、既存の処理（AUTHORIZE FAILED → `cancelOrderForPaymentFailure`）が、注文の取消・在庫の戻し・履歴・お客様への通知の記録を行う。
- カートは与信の完了まで空にならないので、注文し直すと、放置した注文と両方が成立しうる。

### 2.2 PAY.JP の公開仕様（2026-11-25 に openapi.json とガイドを確認。API は呼んでいない）

| 項目 | 内容 |
|---|---|
| 取消 | `POST /v2/payment_flows/{id}/cancel`。理由に `abandoned`（顧客が支払いを完了しなかった場合）を指定できる |
| 取消できない場合 | 400 `invalid_status`、400 `payment_flow_not_cancelable`（すでに処理済み） |
| 取消できる状態の一覧 | **記載が見つからない**。`abandoned` があるため、与信前でも取り消せると考えられるが、テストモードで確かめる（9 章） |
| `processing` | 他の操作をせず完了を待つよう記載がある |
| `canceled` | 他の状態に移らない |
| 放置した Payment Flow の自動失効 | **記載が見つからない**。注文 26 は 3 日以上たっても canceled になっていない |
| 冪等キー | 24 時間以上保持。応答を受け取れなかったときは同じキーで再送すると、初回の応答が返る（処理中なら完了を待つ）。エラーの応答も保存される |

「特定の状態のときだけ取り消す」という条件付きの取消はない。

## 3. 競合と防ぎ方

取消は与信成立後（`requires_capture`）にも効く。「GET で未与信と確認 → 与信が成立して正式受注 → 取消が届く」の順になると、受注済みの注文の与信が失われる。ブラウザの確認操作はサーバーから止められない。そこで、**終了の受付から結果が分かるまで、与信成功の反映と正式受注を止める**（以下「保留」）。

- 保留は、Order のロックの中で記録し、コミットしてから PAY.JP に送る。
- 保留中に与信の成功を観測しても反映しない（DEFERRED）。お客様には「確認中」と表示する。
- 保留を外せるのは、取消を送っていないと確定したとき、または PAY.JP が取消を受け付けなかったと応答したときだけ。
- 送信の直前にもう一度 GET し、与信が成立していれば**送らずに**保留を外し、通常どおり正式受注にする。
- 直前の GET から取消までの間に与信が成立した場合は、取消が勝つことがある。このとき注文は受注されずに終わり、与信も残らない。**与信の優先は保証できない**が、データの矛盾は起きない。

## 4. 状態

新しい表 `unpaid_order_closures`（1 注文に未完了は 1 件）。

| 状態 | 意味 | 次の状態 |
|---|---|---|
| REQUESTED | 受付済み。まだ送っていない（保留中） | SENDING、RELEASED |
| SENDING | 送信する直前に記録。送信中、または結果不明（保留中） | CLOSED、REJECTED |
| CLOSED | canceled を確認し、注文を取り消した | 最終 |
| RELEASED | 送らずにやめた（与信成立、processing など） | 最終 |
| REJECTED | PAY.JP が取消を受け付けなかった | 最終 |

- REQUESTED → SENDING は、現在の状態を条件にした更新で行う。更新できなかった処理は送らない。
- SENDING は、応答がないまま解除しない。定期処理が GET で確かめ、canceled なら CLOSED にする。未確定なら、同じキーで再送する。
- 送信ごとに `unpaid_order_closure_sends`（冪等キー、結果、エラーコード、時刻）を残す。500 など、応答はあったが実行されたか不明なときは、GET のあとで新しいキーの送信を追加する。24 時間を過ぎた送信も同じ扱いにする。
- 400 を受けたら必ず GET する。canceled なら CLOSED、それ以外で `invalid_status`・`payment_flow_not_cancelable` なら REJECTED とする。ほかの 4xx は SENDING のまま管理者に表示する。
- 取消用の payment_transactions は作らない。`PaymentPurposeResolver.matches` は初回与信の決済に取引が 1 件だけあることを求め、ほかの PENDING があると与信の結果（canceled を含む）を反映できなくなるため。

## 5. 142-A：土台と管理者の手動操作

### 5.1 対象

次をすべて満たす注文。受付時に Order、Payment（id 昇順）の順にロックして確認する。

- ORDERED、AUTHORIZED_ACCEPTANCE、`accepted_at` なし、発送準備なし、注文変更なし。
- 有効な決済が PAYJP・CARD の 1 件だけで、PENDING か REQUIRES_ACTION。Payment Flow の ID あり。
- 取引は PENDING の初回与信 1 件だけ。
- `checkout_card_sends` に PENDING・UNCONFIRMED がない。
- 注文から 60 分以上たっている（DB の時計）。

### 5.2 流れ

1. 受付（TX1）：条件を確認し、REQUESTED を記録する。
2. GET（TX の外）。
   - `requires_capture`：RELEASED にしてから、与信の成功を反映する（正式受注）。
   - `processing`：RELEASED。時間をおいてやり直す。
   - `canceled`：送らずに 5 へ進む。
   - `requires_payment_method`・`requires_confirmation`・`requires_action`：3 へ進む。
   - そのほか、または照会の失敗：RELEASED。決済は変えない。
3. 送信の記録（TX2）：条件を再確認し、SENDING と冪等キーを記録する。
4. 取消の POST（TX の外、`abandoned`）→ GET（TX の外）。
5. 反映（TX3）：Order、Payment の順にロックし、canceled を確認した結果を既存の与信失敗の処理で反映し、同じ TX で CLOSED にする。

Webhook と定期照会が先に canceled を観測した場合も、同じ TX で CLOSED にする。

### 5.3 保留中に止めるもの

- 与信成功の反映と正式受注（Webhook、定期照会、決済画面、注文詳細からの再開のすべて）。
- 「カード決済を再開」、決済画面のカード入力、登録カードでの送信、カード登録の準備。

### 5.4 DB トリガー（V110）

- 終了の受付は 5.1 の条件を満たすときだけ挿入できる。状態は 4 章の順にだけ進み、削除・TRUNCATE・内容の書き換えはできない。
- REQUESTED・SENDING がある間は、payments の AUTHORIZED への変更、orders の `accepted_at` の設定、`checkout_card_sends` の挿入を拒否する。
- CLOSED にできるのは、コミット時に注文 CANCELLED・決済 FAILED・取引 FAILED のときだけ。
- 逆に、REQUESTED・SENDING が残ったまま注文を CANCELLED にするコミットも拒否する。

### 5.5 画面

- 管理者の注文詳細に「決済未完了の注文を終了」を追加する。理由の入力欄（任意）と確認画面を付け、状態と送信の記録を表示する。
- 操作した管理者は `unpaid_order_closures` に記録する。注文の状態履歴は、既存の与信失敗と同じ SYSTEM とし、備考は「決済未完了のため注文を終了」にする。
- お客様の注文詳細：保留中は「決済の状態を確認しています」、終了後は「お支払いが完了しなかったため、注文を終了しました」と表示する。
- お客様へのメールは、既存の注文取消のメールのうち、正式受注前の文面（「ご注文は成立しませんでした」）を使う。状態履歴が SYSTEM で正式受注前なら、既存の処理でこの文面になる。

### 5.6 変えないもの

与信成功・失敗の判定、canceled 以外の与信失敗、通常の取消、与信期限切れの取消、注文変更、在庫の計算、141-B の確認。

## 6. 142-B：自動の終了

- 定期処理が、期限を過ぎた対象を 5.2 の流れで終了する。既定は無効。
  - `UNPAID_ORDER_CLOSURE_ENABLED=false`
  - `UNPAID_ORDER_CLOSURE_AFTER=24h`（60 分未満は起動時に拒否）
  - 1 回の件数に上限を付け、1 件の失敗で全体を止めない。RELEASED・REJECTED のあとは間隔を空けて再試行する。
- SENDING の確かめ直しは、自動の終了が無効でも動かす（142-A に含める）。
- 管理者向けに、決済未完了の注文と、止まった終了処理（SENDING のまま、REJECTED）の一覧を追加する。

## 7. テスト

- 条件ごとの受付拒否（アプリと DB トリガーの両方）。60 分の境界。
- 与信の成立との競合：受付前、受付後の GET、GET と POST の間、POST の後。Webhook・定期照会・決済画面のそれぞれ。
- POST の応答：成功、400 の 2 種、ほかの 4xx、500、タイムアウト、ID の不一致。再送で同じキーを使うこと。
- 各 TX の直後に止まった場合の復旧。二重の受付、2 プロセスでの同時実行。REQUESTED の解除と送信が重なっても送らないこと。
- 在庫の戻しと履歴が 1 回だけであること。通知の記録。
- 登録カードの送信との競合。
- 保留の確認とトリガーを外すと、対応するテストが失敗すること（スクラッチのコピー。テストのために DB トリガーを無効にはしない）。
- 回帰の計画は、変更したクラス・表を使うテストを grep で洗い出してから作る。版数の 3 テストを更新する。

## 8. 対象外

- Payment Flow の ID がない PENDING（作成の結果が不明）。既存の管理者確認の対象。
- 決済の行がない ORDERED の注文（作成直後に停止）。開発 DB は 0 件。
- LEGACY の注文、注文変更の与信（注文 17 など）。
- カートが残ることによる注文し直し（二重注文）の防止。終了後は両立しなくなるが、終了までの間は残る。

## 9. 実装前の確認（PAY.JP テストモード、要承認）

注文とは無関係の Payment Flow（100 円、manual）を 1 件作り、`requires_payment_method` で取り消して GET する。取り消せることと、応答の形を確かめる（作成 1 回、取消 1 回、GET 2 回）。カード情報は使わない。

`requires_action`・`requires_confirmation` は、取り消せなければ 400 → REJECTED になるだけなので、事前には確かめない。ブラウザ確認で、3D セキュアの途中で止めた注文を使って確かめる。

取り消せなかった場合は、PAY.JP の終了を前提にしたこの設計は成り立たないので、実装に入らず報告する。

## 12. 142-A の結果（2026-11-25）

## 13. 142-B の結果（2026-11-25）

### 13.1 実装

マイグレーションはない。既定は無効（`UNPAID_ORDER_CLOSURE_ENABLED=false`、`UNPAID_ORDER_CLOSURE_AFTER=24h`）。

| 設計で決めていなかったこと | 実装 |
|---|---|
| 実行の間隔 | 5 分（`UNPAID_ORDER_CLOSURE_FIXED_DELAY`） |
| 1 回の件数 | 20 件、古い注文から |
| RELEASED・REJECTED のあとの間隔 | 6 時間（管理者の操作による終了も同じ） |
| 止まった終了処理 | 直近が REJECTED、または SENDING のまま 10 分以上 |

- 対象は一覧で選び、Order をロックした状態でもう一度判定してから受け付ける（`requestDue`）。受付中・送信中の終了には触れない。

- 一覧は `/admin/unpaid-orders`（読み取りだけ）。管理者トップの件数とメニューのリンクを追加した。
- 60 分に満たない注文、決済の行がない注文も一覧に「終了できません」と表示する。
