## 決定事項（2026-11-19 承認）

1. 権限は `admin_accounts.emergency_shipping_allowed`。付与・取消は運用担当が SQL で行い、アプリは書き込まない。変更は `admin_emergency_shipping_permission_histories` にトリガーで記録する（DB 時計・DB ユーザー）。管理画面は表示だけ。
2. 136-A・B では、緊急出荷も今と同じく注文変更期限（14:00）以降だけ。14:00 前の扱いは 136-C1 で決めた（下記）。
3. V97 より前の管理者による出荷準備（理由の記録なし）は「旧手動準備（理由なし）」と表示し、136-B で固定の対象に含める。
4. 理由は自由記述（必須・500 文字まで）。分類は付けない。

## 136-A の仕組み

### 操作の流れ（`OrderShippingPreparationService.start(orderId, reason, expectedContentRevision)`）

1. 理由（前後の空白を除いて 1〜500 文字）と、画面で確認した注文の版（`content_revision`）を必須にする。
2. 管理者として認証されていること、DB 上で緊急出荷の権限があることを確認する（ログイン時の値ではなく、その時点の DB の値を使う）。
3. Order をロックする。すでに出荷準備に入っていれば、何もせずに「開始済み」を返す（冪等。記録は増えない）。
4. 未解決の注文変更がないこと、決済の条件（カードなら有効な与信が 1 件で、与信期限まで 24 時間超）を確認する。Payment は id の昇順でロックする。
5. 画面を表示した後に注文の版が変わっていれば拒否する。未解決の決済不整合（`payment_discrepancies` が OPEN）があっても拒否する。
6. DB 時計で時刻を読み、変更期限を過ぎていることを確認する。
7. `emergency_shipping_preparations` に記録を書き、そのあと注文の出荷準備 3 列を設定して flush する。

### DB での担保（V97）

- `emergency_shipping_preparations`：1 注文 1 行、追記のみ（UPDATE・DELETE・TRUNCATE は 55000）。
  - INSERT 時に、管理者が有効で権限があり、ユーザー名が一致すること（42501）を確認する。
  - 注文がまだ出荷準備前で、状態が ORDERED または PAID で、変更期限が設定されていることを確認する。
  - 未完了の注文変更 operation、注文変更の受付、PENDING の決済取引、OPEN の決済不整合がないことを確認する（23514）。
  - 注文の写し（状態・版・金額・有効な決済・変更期限）はロック中の行からトリガーが設定する。`created_at` は DB 時計に固定する。
  - コミット時に、注文の出荷準備が記録と一致していることを確認する（遅延トリガー）。
- `orders`：管理者による出荷準備は、対応する記録がなければ拒否する。INSERT の時点で管理者の出荷準備が入った注文は作れない。緊急出荷の出荷準備は、あとから変更・取消できない。
- 権限の履歴は `f136_permission_audit` トリガーだけが書け、追記のみ。

### 136-A の範囲外（意図的に残したもの）

- 決済の条件（有効な与信が 1 件、減額ポリシー）はこれまでどおりアプリで確認する。V97 は競合の防止（未完了の変更・決済処理・不整合）に絞っている。与信期限は V93 の `f135_order_expiry_guard` が担保する。
- 変更期限を過ぎていること（AFTER_DEADLINE）は、アプリだけで確認する（DB は時刻を比べない。次の項目を参照）。
- 記録の `prepared_at`（注文の出荷準備開始時刻と一致させる値）は、DB 時計との前後を DB では比べない。既存テストが、固定時刻の fixture や、アプリの時計を変更期限に固定する方法（受付時刻と変更期限は V81 で変更できない）を使っているため。操作時刻の監査には、トリガーが DB 時計で設定する `created_at` を使う。アプリでは `prepared_at` に DB 時計の値を使う。
- 注文内容の固定は 136-B で行う。

## 136-B の仕組み（2026-11-20 承認）

- V98：V86 の `f131_order_preparation_guard` と `f131_prepared_content_guard` を置き換え、出荷準備の開始時刻が入っているすべての注文（倉庫出力・緊急出荷・V97 より前の管理者による準備）を固定する。固定する項目は V86 と同じ（出荷準備の情報・顧客・金額・版・配送先・有効な決済、CANCELLED への変更、明細と料金の追加・変更・削除。エラーコードは 55000）。既存の行は書き換えない。
- アプリ：`Order.requireContentMutable()` を、内容を変えるメソッド（金額・版・明細・料金・配送先・有効な決済の変更とキャンセル）と、`OrderItem`・`OrderCharge` の変更メソッドから呼ぶ。出荷準備後は `InvalidOrderStatusException` で拒否する。
- 出荷準備後にキャンセルする方法はない（設計資料 4.2 章の「出荷準備の取消禁止」）。出荷準備後に出荷できなくなった注文（与信期限切れ・在庫切れなど）のための「出荷中止」の手順は、今後の Feature の候補とする。
- テスト：出荷準備を扱う 56 クラスのうち、6 クラスを直した。出荷準備後に変更・キャンセルしていた fixture は、変更を出荷準備の前に移すか、DB とエンティティが拒否することを確かめる形にした。多重防御を試す単体テストは、フィールドを直接設定して状態を作る。

## 136-C1 の仕組み（2026-11-20 承認）

- 136-A の「変更期限後の緊急出荷」（`AFTER_DEADLINE`）に加えて、14:00 以降に正式受付した注文（変更期限が翌日 14:00）を、受付当日に限り、翌日の 14:05 出力を待たずに緊急出荷できる（`SAME_DAY`）。
- 管理者のコメント（理由）は両方の種類で必須。お客様の了承のチェックは設けない。追加のメールは送らず、出荷完了時の ORDER_SHIPPED メール（V91）で知らせる。
- アプリ：`OrderModificationPolicy.allowsSameDayEmergency` が、正式受付（`AUTHORIZED_ACCEPTANCE`）、変更期限が受付日の翌日 14:00、操作時刻が受付日のうちで受付時刻以降・変更期限前であることを確認する。変更期限後なら `AFTER_DEADLINE`、当日の条件を満たせば `SAME_DAY`、どちらでもなければ拒否する。
- 画面：注文詳細に、当日出荷の対象であることと、開始後はお客様が変更・キャンセルできなくなることを表示する。開始後は「緊急出荷の種類」を表示する。
- DB（V99）：`emergency_shipping_preparations` に `mode`（既定 `AFTER_DEADLINE`。V99 より前の行もこの値）、`accepted_at`、`observed_before_deadline` を追加した。`SAME_DAY` の記録は、正式受付で、変更期限が受付日の翌日 14:00、`prepared_at` が受付日のうちで受付時刻以降・変更期限前でなければ拒否する（23514）。受付時刻と、操作が DB 時計で変更期限前だったか（`observed_before_deadline`）はトリガーが設定する。

## 136-C2 の仕組み（2026-11-20 承認）

- 緊急出荷の注文ごとに、14:05 の倉庫向け CSV と同じ形式（ヘッダー・列・UTF-8 BOM・CRLF・明細ごと 1 行）の CSV を、管理画面の注文詳細からダウンロードできる。すべての管理者がダウンロードできる（緊急出荷権限は不要）。
  - バッチID 列は `E` + 緊急出荷記録の id、業務日 列は緊急出荷の操作日（`prepared_at` の日付）。
  - 行は注文と明細から作る。出荷準備後の注文は V98 で固定されるので、何度ダウンロードしても同じ内容になる。明細の並びは倉庫出力（V86）と同じ明細 id 順。
  - ファイル名は `emergency-shipping-<注文番号>-<yyyyMMdd-HHmmss>.csv`（DB 時計のダウンロード時刻）。毎回別の名前になり、前のファイルを上書きしない。
- 監査（V100 `emergency_shipping_csv_downloads`）：ダウンロードごとに 1 行、追記のみ（55000）。管理者・DB 時計の時刻・行数・業務日・ファイル名・SHA-256 を記録する。
  - 注文が緊急出荷の記録どおりに出荷準備されていて版が同じこと、行数が明細数と一致し業務日が操作日であること（23514）、管理者が有効で名前が一致すること（42501）を確認する。時刻とファイル名はトリガーが DB 時計で決める。
- 注文詳細に、ダウンロードボタンとダウンロード履歴（日時・管理者・行数・ファイル名）を表示する。一覧画面とダッシュボードの件数は 136-C3 で作る。
- V97 より前の管理者による出荷準備（記録なし）は対象外。

## 136-C3 の仕組み（2026-11-21 承認）

- 緊急出荷一覧（`/admin/emergency-shipments`、管理画面のヘッダーから開く）：注文番号・種類・操作日時（記録の `created_at`）・管理者・理由・出荷状態・CSV のダウンロード回数と最終日時を、新しい順に 50 件ずつ表示する。
  - 絞り込み：操作日の期間（パラメータなしで開くと直近 30 日。期間を空欄にすると全期間）、出荷状態（すべて／未出荷／出荷済み）、CSV（すべて／未ダウンロード）。
  - 同じ画面に、今の権限保有者と権限の変更履歴（新しい順に 100 件）を表示する。表示だけで、変更は SQL で行う。
- ダッシュボード（決済要対応の表）：「緊急出荷・未出荷」（出荷済みでもキャンセルでもない）と「緊急出荷・CSV 未ダウンロード（未出荷）」の件数。それぞれ絞り込み済みの一覧へリンクする。件数を取得できなくてもダッシュボードは表示する。
- お客様の注文詳細：出荷準備に入った未出荷の注文（緊急出荷・倉庫出力の両方）では、変更・キャンセル・配送先変更の操作と「〜まで変更できます」を出さず、「出荷準備に入ったため、注文の変更・キャンセルはできません。」と表示する。`OrderService` の 4 つの判定（変更期間中か、キャンセル・明細変更・配送先変更ができるか）に「出荷準備前であること」を加えたので、入力画面へ入るときの確認にも効く。C-1 の当日出荷では変更期限前に出荷準備に入るため、この対応が必要になった（操作自体はサービス・エンティティ・DB で拒否されていた）。

- 注文詳細の緊急出荷用 CSV ボタン（ブラウザ確認での指摘を受けて追加）：通常のフォーム送信では添付ファイルが返るだけで画面が更新されず、ダウンロード履歴が再読み込みまで古いままだった。JS で CSV を受け取って保存したあと画面を再読み込みする。CSV 以外の応答（拒否のリダイレクト、403）や JS が使えない場合は、従来のフォーム送信になる。

## 倉庫向け注文データ CSV との関係

緊急出荷の注文は、14:05 の倉庫向け注文データ出力（Feature131）には出力されない（決定事項：手動で準備した注文は自動出力しない）。出力対象の抽出（出荷準備前の注文だけ）、注文ごとの保留（`MANUALLY_PREPARED`）、V86 の出力行トリガー（自動の出荷準備だけ）の 3 段階で除外される。倉庫へは個別に連絡する（136-C2 の注文ごとの CSV を使う）。管理画面の注文一覧 CSV（`OrderCsvService`）は倉庫向けではなく、緊急出荷の注文も含む。

## 運用：権限の付与・取消

アプリを止める必要はない。変更は次のログインを待たずに有効になる（操作のたびに DB の値を確認するため）。

```sql
-- 付与
UPDATE admin_accounts SET emergency_shipping_allowed = TRUE WHERE username = '<管理者名>';
-- 取消
UPDATE admin_accounts SET emergency_shipping_allowed = FALSE WHERE username = '<管理者名>';
-- 履歴の確認
SELECT a.username, h.allowed, h.changed_at, h.changed_by_db_user
FROM admin_emergency_shipping_permission_histories h JOIN admin_accounts a ON a.id = h.admin_account_id
ORDER BY h.id;
```

## 確認用 SQL

```sql
SELECT r.order_id, r.mode, r.admin_username, r.reason, r.prepared_at, r.created_at, r.order_status,
       r.content_revision, r.total_amount, r.accepted_at, r.observed_before_deadline
FROM emergency_shipping_preparations r ORDER BY r.id DESC;
```
