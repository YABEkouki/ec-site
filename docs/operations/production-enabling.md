# 本番で有効にするための手順書

対象：本番と検証の環境を用意する運用担当。基準は main 7786db3（最新マイグレーション V113）。設計は `docs/feature145/production-enabling.md`。

この手順書には、キー・パスワード・メールアドレスの値を書かない。値は環境ごとの安全な場所で管理する。

## 1. はじめに

- 外部に影響する処理は、既定ですべて止めてある。影響する先は PAY.JP への POST、メール、倉庫へのファイルである。
- どの処理も、環境変数を `true` にしてアプリを再起動すると動く。画面からは切り替えられない。
- 止めるときは、環境変数を `false` に戻して再起動する。
- 止めているあいだも、多くの処理は記録だけを作る。有効にした時点で、たまった記録を古い順に処理する。処理ごとの扱いは 4 章に書く。
- 有効にしたら、管理画面の「運用の状態」（`/admin/operations`、145-B で追加）と、4 章の「確かめるところ」を見る。

## 2. 前提の確認

処理を有効にする前に、次をすべて確かめる。

### 2.1 データベース（PostgreSQL 17）

- `track_commit_timestamp`、`fsync`、`synchronous_commit` がすべて on であること。Feature125 の承認の前提になる。
- Flyway は、アプリの起動のときに自動で適用される。`flyway repair` や DB の初期化はしない。
- DB を再起動すると、Feature125 の runtime の承認が無効になる（2.5）。

### 2.2 PAY.JP

| 設定（環境変数） | 内容 | 確かめること |
|---|---|---|
| `PAYJP_SECRET_KEY`、`PAYJP_PUBLIC_KEY` | API キー | 本番は `sk_live_`・`pk_live_` で始まる。テストのキーが混ざっていない |
| `PAYJP_WEBHOOK_TOKEN` | Webhook の検証用トークン | PAY.JP の管理画面の Webhook に `<base-url>/webhooks/payjp` を登録し、同じトークンを設定する |
| `PAYJP_CAPTURECONNECTION_MODE` ほか `PAYJP_CAPTURECONNECTION_*` | 売上確定の接続 | 本番は `LIVE`。モードと API キーの種類（`sk_live_`・`pk_live_`）、API の接続先が合わないと、売上確定と取消の送信のたびに拒否される（起動では確かめない）。どのアカウントのキーかまでは、アプリでは確かめられないので、運用で照合する |
| `PAYJP_CUSTOMER_ID_PREFIX` | 保存カードの顧客 ID の接頭辞 | 環境ごとに別の値にする（開発と本番で同じ PAY.JP アカウントを使う場合の混同を防ぐ）。空にすると保存カードは使えない |

### 2.3 メールと URL

- `spring.mail.host`・`port`・`username`・`password`、TLS の設定：本番の SMTP に向ける。開発の既定は mailpit（localhost:1025）。
- `app.mail.from`：差出人。
- `app.base-url`：メールの本文のリンクに使う。本番の URL にする。

### 2.4 監査記録の署名キー

- `PAYMENT_AUDIT_HANDLING_HMAC_KEY`、`PAYMENT_AUDIT_MANUAL_RESEND_HMAC_KEY`：決済照合の通知の対応記録と、手動再送に使う。
- どちらも 32 バイト以上にする。形式が違うと、アプリは起動しない。空のときは、その操作が使えない。

### 2.5 Feature125（一括編集）の runtime

- SQL の手順で承認する：`scripts/order-edit-runtime.sql`、手順は `docs/feature125/operational-runtime.md`。アプリの起動では承認されない。
- 承認していないあいだは、次のものが止まる：一括編集の受付と実行、その結果の反映、自動で終わらせる処理の一部（4 章の 4・5）。読み取りの表示は使える。
- DB を再起動したあとは、同じ世代で承認し直す（`status` → `probe` → `check` → `enable`）。新しい世代は作らない。

### 2.6 本番では変える設定

- `spring.jpa.show-sql=true`、`spring.jpa.properties.hibernate.format_sql=true`：SQL をすべてログに出す。本番では `false` にする。
- `spring.thymeleaf.cache=false`：画面のテンプレートを毎回読み直す。本番では `true` にする。

これらは今 `application.properties` に直接書いてあり、環境変数では変えられない。本番の設定ファイル（`--spring.config.additional-location` など）で上書きする。

## 3. 有効にする順番

1 つずつ有効にし、そのたびに 4 章の「確かめるところ」で動作を確かめてから次へ進む。

| 順 | 処理 | 理由 |
|---|---|---|
| 1 | 決済照合の通知メール（4.1） | 決済の異常に気づけるようにする |
| 2 | お客様への注文メール（4.2） | 注文・出荷・取消をお客様に知らせる |
| 3 | 与信期限の更新（4.3） | PAY.JP への GET だけ。記録の期限を正確にする |
| 4 | 未払い注文の自動終了（4.4） | PAY.JP に取消を送る。2.5 の承認とは関係しない |
| 5 | 終わらなかった注文変更の自動終了（4.5） | PAY.JP に取消を送る。2.5 の承認が必要 |
| 6 | 14:05 の倉庫向け出力（4.6） | 対象の注文の内容が固まる |
| 7 | 倉庫ファイルの書き出し（4.7） | 6 の結果をファイルにする |
| 8 | 出荷済み CSV の取り込みと出荷（4.8） | PAY.JP に売上の確定を送る |

既定で動いている処理（4.9）は止めない。

## 4. 処理ごとの説明

### 4.1 決済照合の通知メール（運用担当あて）

- 何をするか：決済照合の監査（4.9）で見つかった不一致を、運用担当にメールで知らせる。
- 外部への影響：メール。
- 設定：
  - `PAYMENT_AUDIT_NOTIFICATION_ENABLED`（既定 false）
  - `PAYMENT_AUDIT_NOTIFICATION_RECIPIENTS`：宛先。有効にするときは 1〜20 件が必須。表示名なしの単一のアドレスで書く。0 件だとアプリは起動しない。
  - `PAYMENT_AUDIT_NOTIFICATION_FIXED_DELAY`（1m）、`_RETRY_DELAY`（5m）、`_MAX_ATTEMPTS`（3）
  - SMTP のタイムアウト：`_SMTP_*`
- 前提：2.3、2.4。
- 確かめるところ：
  - 管理画面「決済監査メール通知送信履歴」（`/admin/payment-audit-notifications`）で、送信の結果を見る。
  - 受信側で、メールが届くことを確かめる。
- 止めたとき：新しい通知は送られない。不一致は監査の画面で見られる。

### 4.2 お客様への注文メール

- 何をするか：注文の受付、出荷、取消、注文変更の結果などを、お客様にメールで知らせる。
- 外部への影響：メール。
- 設定：
  - `CUSTOMER_NOTIFICATION_ENABLED`（既定 false）
  - `CUSTOMER_NOTIFICATION_FIXED_DELAY`（30s）
  - `CUSTOMER_NOTIFICATION_MAX_AGE`（24h）
- 前提：2.3。
- **有効にしたときの注意**：止めているあいだも、送る記録は作られている。有効にすると、作られてから 24 時間以内の記録が送られる。それより古い記録は送られず、期限切れになる。
- 確かめるところ：管理画面「お客様へのメール通知」（`/admin/customer-notifications`）で、送信の結果（送信済み、失敗、期限切れ）を見る。
- 止めたとき：記録は作られ続ける。再び有効にすると、24 時間以内のものだけが送られる。

### 4.3 与信期限の更新

- 何をするか：与信の期限が推定値の決済について、PAY.JP の `expired_at` を GET で読み、記録を置き換える。
- 外部への影響：PAY.JP への GET だけ。
- 設定：
  - `AUTHORIZATION_EXPIRY_REFRESH_ENABLED`（既定 false）
  - `AUTHORIZATION_EXPIRY_REFRESH_FIXED_DELAY`（10m）
  - 1 回の件数：20
  - 記録できない応答のあとは、同じ決済を 6 時間問い合わせない。この待ちはアプリ内だけで持つので、再起動で消える。
- 確かめるところ：管理画面の注文の一覧で、与信期限の表示と絞り込みを見る。ダッシュボードで、期限切れと期限間近の件数を見る。
- 止めたとき：期限は推定値のまま（与信から 5 日）。出荷準備などの期限の判定は、推定値で行われる。

### 4.4 未払い注文の自動終了

- 何をするか：決済が完了しないまま一定時間たった注文について、PAY.JP の Payment Flow を取り消し、注文を終わらせる。
- 外部への影響：PAY.JP への取消（POST）、在庫の戻し。
- 設定：
  - `UNPAID_ORDER_CLOSURE_ENABLED`（既定 false）
  - `UNPAID_ORDER_CLOSURE_AFTER`（24h。60 分以上）
  - `UNPAID_ORDER_CLOSURE_FIXED_DELAY`（5m）
  - 1 回の件数：20、再試行の間隔：6 時間
- 前提：2.2。
- 確かめるところ：管理画面「決済未完了の注文一覧」（`/admin/unpaid-orders`）で対象の注文を見て、注文詳細で終了の記録を見る。
- 止めたとき：自動では終わらない。管理者が注文詳細で 1 件ずつ終わらせられる。送信中の取消の確かめ直しは、止めていても決済の照合（4.9）が行う。

### 4.5 終わらなかった注文変更の自動終了

- 何をするか：お客様が再与信（3D セキュアなど）を最後まで終えなかった一括編集の注文変更について、自動処理の期限を過ぎてから一定時間たったら、新しい Payment Flow を取り消して変更を終わらせる。在庫を戻し、注文は変更前の内容に戻る。
- 外部への影響：PAY.JP への取消（POST）、在庫の戻し。
- 設定：
  - `ORDER_CHANGE_CLOSURE_ENABLED`（既定 false）
  - `ORDER_CHANGE_CLOSURE_AFTER`（60m。10 分以上 7 日以下）
  - `ORDER_CHANGE_CLOSURE_FIXED_DELAY`（5m）
  - 1 回の件数：20、再試行の間隔：6 時間
- 前提：2.2、2.5（承認がないと何もしない）。
- 確かめるところ：管理画面の注文詳細で、注文変更の終了の記録を見る（依頼者は SYSTEM、備考は「自動終了」と表示される）。
- 止めたとき：自動では終わらない。管理者が注文詳細で 1 件ずつ終わらせられる。新しい与信が期限切れになった変更は、自動の対象外で、管理者の操作だけで終わらせる（Feature144）。

### 4.6 14:05 の倉庫向け出力と自動の出荷準備

- 何をするか：毎日 14:05 以降に、変更の期限（14:00）を過ぎた注文をまとめてバッチにする。対象の注文を自動で出荷準備にする。条件に合わない注文は保留にし、翌日の 14:05 にもう一度判定する。
- 外部への影響：対象の注文の内容が固まる（変更や取消ができなくなる）。ファイルの書き出しは 4.7 が行う。
- 設定：
  - `WAREHOUSE_EXPORT_ENABLED`（既定 false）
  - `WAREHOUSE_EXPORT_START_DATE`（yyyy-MM-dd）：有効にするときは必須。空だとアプリは起動しない。変更の期限がこの日より前の注文は、自動で出力しない。本番の運用を始める日を入れる。
  - `WAREHOUSE_EXPORT_FIXED_DELAY`（1m）：14:05 前と、その日のバッチが締まったあとは、何もしない。
- 確かめるところ：
  - 管理画面「倉庫向け注文データ出力」（`/admin/warehouse-exports`）で、その日のバッチと行を見る。
  - 「注文変更による出荷保留一覧」（`/admin/order-holds`）で、保留の理由を見る。
- 止めたとき：自動の出力と出荷準備は行われない。緊急出荷（`/admin/emergency-shipments`）は、止めていても使える。

### 4.7 倉庫ファイルの書き出し

- 何をするか：4.6 と緊急出荷の出力を、倉庫が FTP で回収するフォルダーにファイル（ヘッダーと明細）として書き出す。
- 外部への影響：ファイル。
- 設定：
  - `WAREHOUSE_FILE_ENABLED`（既定 false）
  - `WAREHOUSE_FILE_OUTPUT_DIR`、`WAREHOUSE_FILE_WORK_DIR`：有効にするときは必須。空だとアプリは起動しない。作業フォルダーは、出力フォルダーと同じファイルシステムで、出力フォルダーの外に置く（一時ファイルを出力フォルダーへ原子的に移すため）。
  - `WAREHOUSE_FILE_FIXED_DELAY`（1m）、再試行の間隔：5 分、試行の上限：12 回
- 前提：4.6（または緊急出荷の運用）。
- 確かめるところ：
  - 「倉庫向け注文データ出力」の画面で、ファイルの出力の状態と失敗の理由を見る。
  - 出力フォルダーにファイルができることを確かめる。
- 止めたとき：出力の記録は待ちのまま作られる。有効にすると古い順に書き出す。

### 4.8 出荷済み CSV の取り込みと出荷

- 何をするか：管理者がアップロードした出荷済み CSV の行について、注文を出荷済みにし、PAY.JP に売上の確定を送る。
- 外部への影響：PAY.JP への売上確定（POST）、お客様への出荷メール（4.2 が有効なとき）。
- 設定：
  - `WAREHOUSE_SHIPMENT_IMPORT_ENABLED`（既定 false）
  - `WAREHOUSE_SHIPMENT_IMPORT_FIXED_DELAY`（1m）
  - 試行の上限：3 回、1 回の件数：50
- 前提：2.2、4.6・4.7（出力した行だけを受け付ける）。
- 確かめるところ：管理画面「倉庫出荷取込み」（`/admin/warehouse-shipments`）で、行ごとの結果を見る。
- 止めたとき：アップロードと行の判定はできる。出荷と売上の確定は、有効にするまで待つ。

### 4.9 既定で動いている処理（止めない）

- **決済の照合**（`app.payment.reconciliation.enabled=true`、1 分ごと）：PAY.JP の結果が届いていない決済を GET で確かめる。注文変更の後片付けもここで行う（不採用の取消と終了、最終判定、新しい Flow の後片付け、4.4・4.5 の送信の回復）。
- **決済照合の監査**（`app.payment.discrepancy-audit.enabled=true`、5 分ごと）：DB と PAY.JP の不一致を記録する。管理画面「PAY.JP定期決済監査履歴」（`/admin/payment-discrepancy-audits`）で、実行の記録と遅れを見る。
- **手動再送のスケジュール**（`manual-resend-scheduler-enabled=true`）。

これらは `application.properties` に直接 `true` で書いてある。止める必要があるときは、本番の設定ファイルで上書きする。

## 5. 再起動と障害のとき

- **アプリの再起動**：設定はそのまま引き継がれる。Feature125 の承認も残る。送信の途中で止まったものは、決済の照合と各処理が、GET で確かめてから続ける（同じ要求を確かめずに送り直すことはない）。
- **DB の再起動**：Feature125 の承認が無効になる（2.5）。アプリを止め、承認し直してから起動する。承認し直すまで、4.5 は何もしない。一括編集の照会では、エラーのログが繰り返し出る。
- **PAY.JP やメールの障害**：各処理は、次回に再試行する。上限を超えたものは、画面に失敗として残る。復旧後に画面で確かめる。
- **処理を止めたいとき**：環境変数を `false` にして再起動する。処理中の 1 件は、その処理の手順で最後まで進むか、次の起動のときに確かめ直される。

## 6. 開発環境での注意

- `./start-dev.sh` は `.env` を読んでからアプリを起動する。`.env` に書いていない処理は止まったまま。
- 一時的に有効にしたいときは、環境変数を前に付けて起動する（例：`CUSTOMER_NOTIFICATION_ENABLED=true ./start-dev.sh`）。こうすると `.env` を変えずに済む。
- メールは mailpit（http://localhost:8025）に届く。
- PAY.JP はテストモード（`sk_test_`）。起動のときに、照合の GET が発生する。
